# 需求文档

## 简介

内部数据分析工具是一个面向公司内部员工的数据分析平台，集成 RAG（检索增强生成）知识检索、LLM 智能体问答与数据报表分析功能。系统通过 RAG 检索相关文档后，调用大语言模型生成结构化回答，支持本地部署模型（Ollama/vLLM）和云端 API（OpenAI/通义千问/文心一言）两种接入方式。该系统对数据私密性有严格要求，采用 RBAC 权限控制模型，确保不同部门和岗位的员工只能访问其权限范围内的数据。技术栈采用 Vue 前端、Python 后端，结合 ChromaDB、MySQL 和 Milvus 数据库。

## 术语表

- **分析平台**: 内部数据分析工具的核心系统，负责数据检索、报表生成和权限管理
- **RAG引擎**: 检索增强生成模块，负责从知识库中检索相关文档片段并辅助生成回答
- **LLM服务**: 大语言模型调用服务，负责接收检索结果和用户问题，调用 LLM 生成结构化回答
- **LLM网关**: 统一的 LLM 接入层，负责路由请求到不同的模型后端（本地模型或云端 API）
- **对话管理器**: 管理多轮对话上下文的模块，维护会话历史并构建包含上下文的 Prompt
- **Prompt模板引擎**: 管理和渲染不同业务场景下 Prompt 模板的子系统
- **Token监控服务**: 监控 LLM 调用的 Token 用量、统计成本并执行配额控制的服务
- **报表模块**: 负责数据报表的生成、展示和导出功能的子系统
- **权限服务**: 基于 RBAC 模型的权限控制服务，管理用户角色、权限分配和数据访问控制
- **知识库**: 存储在向量数据库（ChromaDB/Milvus）中的企业内部文档和数据索引
- **RBAC**: 基于角色的访问控制（Role-Based Access Control），通过角色分配权限
- **数据安全层**: 负责数据加密、访问审计和防泄露保护的安全子系统
- **内部员工**: 公司内部经过身份验证的系统用户
- **管理员**: 拥有系统配置、用户管理和全局数据访问权限的高级用户角色
- **部门用户**: 仅拥有本部门数据访问权限的普通用户角色
- **本地模型**: 部署在内网环境中的 LLM 模型实例（如通过 Ollama 或 vLLM 部署）
- **云端LLM**: 通过 API 调用的外部大语言模型服务（如 OpenAI、通义千问、文心一言）
- **Prompt注入**: 恶意用户通过构造特殊输入试图操纵 LLM 行为的攻击方式

## 需求

### 需求 1：RAG 知识检索

**用户故事：** 作为内部员工，我希望通过自然语言提问检索企业知识库中的相关信息，并由 LLM 生成结构化回答，以便快速获取工作所需的知识和数据。

#### 验收标准

1. WHEN 内部员工提交自然语言查询请求, THE RAG引擎 SHALL 从知识库中检索语义相关的文档片段并传递给 LLM服务
2. WHEN RAG引擎完成文档检索, THE LLM服务 SHALL 基于检索到的文档片段生成结构化回答，包含摘要、关键要点和信息来源引用
3. WHEN LLM服务生成回答, THE 分析平台 SHALL 展示生成的回答内容及其引用的原始文档来源信息和相关度评分
4. WHILE 内部员工执行知识检索, THE 权限服务 SHALL 过滤掉该用户无权访问的文档片段，确保 LLM服务 仅基于用户有权访问的文档生成回答
5. WHEN 内部员工提交查询请求, THE 分析平台 SHALL 在 10 秒内返回 LLM 生成的完整回答
6. IF 知识库中无匹配结果, THEN THE 分析平台 SHALL 向用户展示明确的无结果提示信息，不调用 LLM服务 生成回答
7. IF LLM服务 调用失败或超时, THEN THE 分析平台 SHALL 降级展示 RAG引擎 检索到的原始文档片段并提示用户 LLM 服务暂时不可用

### 需求 2：数据报表分析

**用户故事：** 作为内部员工，我希望能够查看和生成数据分析报表，以便对业务数据进行分析和决策支持。

#### 验收标准

1. WHEN 内部员工选择报表类型并指定数据范围, THE 报表模块 SHALL 生成对应的数据报表并展示可视化图表
2. THE 报表模块 SHALL 支持表格、折线图、柱状图和饼图四种可视化展示方式
3. WHEN 内部员工请求导出报表, THE 报表模块 SHALL 生成 Excel 或 PDF 格式的报表文件供下载
4. WHILE 报表数据加载中, THE 分析平台 SHALL 展示加载进度指示
5. WHEN 内部员工访问报表页面, THE 权限服务 SHALL 仅展示该用户角色有权访问的数据维度和指标
6. IF 报表生成过程中发生数据源连接失败, THEN THE 报表模块 SHALL 记录错误日志并向用户展示友好的错误提示

### 需求 3：RBAC 权限管理

**用户故事：** 作为管理员，我希望能够配置基于角色的访问控制策略，以便确保不同部门和岗位的员工只能访问其权限范围内的数据。

#### 验收标准

1. THE 权限服务 SHALL 支持创建、编辑和删除角色，每个角色包含一组数据访问权限定义
2. WHEN 管理员将角色分配给用户, THE 权限服务 SHALL 立即生效该用户的新权限配置
3. THE 权限服务 SHALL 支持按部门、岗位维度定义数据访问范围
4. WHEN 内部员工登录系统, THE 权限服务 SHALL 加载该用户所属角色的全部权限配置
5. WHILE 用户无任何角色分配, THE 权限服务 SHALL 拒绝该用户访问任何业务数据
6. WHEN 管理员修改角色权限, THE 权限服务 SHALL 记录权限变更的审计日志，包含操作人、操作时间和变更内容
7. IF 权限配置存在冲突（同一用户的多个角色对同一数据有不同权限）, THEN THE 权限服务 SHALL 采用最高权限优先原则进行合并

### 需求 4：用户认证与身份管理

**用户故事：** 作为内部员工，我希望通过安全的身份认证方式登录系统，以便确保只有经授权的人员能够访问系统。

#### 验收标准

1. WHEN 内部员工提交登录凭证, THE 分析平台 SHALL 验证身份信息并在验证通过后签发认证令牌
2. THE 分析平台 SHALL 支持与企业现有身份认证系统（如 LDAP/AD）集成
3. WHEN 认证令牌过期, THE 分析平台 SHALL 要求用户重新登录
4. WHEN 同一账号在 1 分钟内连续 5 次登录失败, THE 分析平台 SHALL 锁定该账号 15 分钟
5. IF 用户会话超过 30 分钟无操作, THEN THE 分析平台 SHALL 自动终止该会话并要求重新认证

### 需求 5：数据安全与隐私保护

**用户故事：** 作为管理员，我希望系统具备完善的数据安全保护机制，以便防止敏感数据泄露并满足公司数据安全合规要求。

#### 验收标准

1. THE 数据安全层 SHALL 对存储在 MySQL 中的敏感数据字段进行 AES-256 加密存储
2. THE 数据安全层 SHALL 对分析平台与数据库之间的所有通信使用 TLS 1.2 及以上版本加密传输
3. WHEN 用户执行数据查询或导出操作, THE 数据安全层 SHALL 记录完整的操作审计日志，包含用户身份、操作时间、操作类型和涉及数据范围
4. THE 数据安全层 SHALL 对向量数据库（ChromaDB/Milvus）中的文档索引实施访问控制标记
5. IF 检测到异常数据访问模式（如短时间内大量数据导出）, THEN THE 数据安全层 SHALL 触发安全告警并通知管理员
6. THE 数据安全层 SHALL 禁止将任何业务数据传输至外部网络或第三方服务
7. WHEN 管理员配置数据备份策略, THE 数据安全层 SHALL 对备份数据同样实施加密保护

### 需求 6：系统性能与可用性

**用户故事：** 作为内部员工，我希望系统具有良好的响应速度和稳定性，以便高效完成日常数据分析工作。

#### 验收标准

1. WHEN 内部员工发起页面请求, THE 分析平台 SHALL 在 3 秒内完成页面渲染
2. THE 分析平台 SHALL 支持至少 100 个用户并发访问而不产生明显性能下降
3. WHILE 系统处于正常运行状态, THE 分析平台 SHALL 保持 99.5% 以上的月度可用率
4. WHEN 报表模块处理大数据量查询（超过 10 万条记录）, THE 报表模块 SHALL 采用分页加载方式并在 10 秒内返回首页数据
5. IF 系统组件发生故障, THEN THE 分析平台 SHALL 自动进行故障隔离，确保其他功能模块正常运行

### 需求 7：技术架构约束

**用户故事：** 作为管理员，我希望系统采用明确的技术架构方案，以便支持后续维护、扩展和部署。

#### 验收标准

1. THE 分析平台 SHALL 使用 Vue 框架构建前端用户界面
2. THE 分析平台 SHALL 使用 Python 语言开发后端服务
3. THE 分析平台 SHALL 使用 MySQL 存储结构化业务数据和用户权限数据
4. THE RAG引擎 SHALL 使用 ChromaDB 或 Milvus 作为向量数据库存储文档嵌入向量
5. THE 分析平台 SHALL 采用前后端分离架构，前端通过 RESTful API 与后端通信
6. THE 分析平台 SHALL 支持纯内网部署方案和云服务器加安全加固部署方案两种部署模式

### 需求 8：部署方案对比支持

**用户故事：** 作为管理员，我希望在文档中了解纯内网部署与云服务器+安全加固两种方案的对比，以便做出合理的部署决策。

#### 验收标准

1. WHERE 选择纯内网部署方案, THE 分析平台 SHALL 支持在无外网连接的环境下独立运行全部功能
2. WHERE 选择云服务器加安全加固方案, THE 分析平台 SHALL 通过 VPN、防火墙规则和网络隔离确保数据传输安全
3. WHERE 选择纯内网部署方案, THE 分析平台 SHALL 提供离线模型加载和本地知识库更新机制
4. WHERE 选择云服务器加安全加固方案, THE 数据安全层 SHALL 实施 IP 白名单、DDoS 防护和入侵检测措施
5. THE 分析平台 SHALL 在两种部署方案下均满足相同的数据安全和权限控制要求
6. WHERE 选择云服务器加安全加固方案, THE 数据安全层 SHALL 对所有数据存储节点实施物理隔离或逻辑隔离

### 需求 9：LLM 智能体问答

**用户故事：** 作为内部员工，我希望通过自然语言与系统进行问答交互，系统基于检索到的相关文档调用 LLM 生成结构化、易理解的回答，而非仅返回原始文档片段。

#### 验收标准

1. WHEN 内部员工输入自然语言问题, THE LLM服务 SHALL 接收 RAG引擎 检索到的相关文档片段并生成包含摘要、关键结论和来源引用的结构化回答
2. THE LLM服务 SHALL 在生成回答时标注每个关键信息点对应的原始文档来源
3. WHEN LLM服务生成回答, THE 分析平台 SHALL 以清晰的格式展示回答正文、要点列表和参考来源
4. WHILE LLM服务 正在生成回答, THE 分析平台 SHALL 以流式方式逐步展示生成内容，提供实时反馈
5. IF LLM服务 生成的回答与检索文档相关度低于设定阈值, THEN THE 分析平台 SHALL 提示用户该回答可能不够准确并展示原始检索文档供参考
6. WHEN 内部员工对回答不满意, THE 分析平台 SHALL 提供重新生成功能，允许用户要求 LLM服务 基于相同检索结果生成新的回答

### 需求 10：LLM 模型管理

**用户故事：** 作为管理员，我希望系统支持多种 LLM 接入方式，包括本地部署模型和云端 API，以便根据安全需求和性能要求灵活选择合适的模型。

#### 验收标准

1. THE LLM网关 SHALL 支持接入本地部署的 LLM 模型（通过 Ollama 或 vLLM 框架部署）
2. THE LLM网关 SHALL 支持接入云端 LLM API（包括 OpenAI、通义千问、文心一言）
3. WHEN 管理员配置新的 LLM 模型接入, THE LLM网关 SHALL 验证连接可用性并返回配置结果
4. THE LLM网关 SHALL 支持配置模型优先级，当首选模型不可用时自动切换到备选模型
5. WHEN 管理员修改 LLM 模型配置, THE LLM网关 SHALL 在不中断当前会话的前提下平滑切换模型
6. THE 分析平台 SHALL 提供 LLM 模型管理界面，展示每个已接入模型的状态、响应延迟和可用性信息
7. IF 所有配置的 LLM 模型均不可用, THEN THE LLM网关 SHALL 向分析平台返回服务不可用状态并记录告警日志

### 需求 11：对话上下文管理

**用户故事：** 作为内部员工，我希望系统支持多轮对话，能够记住之前的提问内容和回答，以便进行连续追问和深入讨论。

#### 验收标准

1. WHEN 内部员工在同一会话中提出后续问题, THE 对话管理器 SHALL 将历史对话上下文纳入当前 Prompt 构建
2. THE 对话管理器 SHALL 维护每个会话最近 20 轮对话记录作为上下文窗口
3. WHEN 对话上下文超出 LLM 模型的 Token 限制, THE 对话管理器 SHALL 对早期对话内容进行摘要压缩以保留关键信息
4. WHEN 内部员工主动结束会话或开启新会话, THE 对话管理器 SHALL 清空当前上下文并开始新的对话轮次
5. THE 分析平台 SHALL 展示当前会话的完整对话历史，支持内部员工回顾之前的问答内容
6. IF 用户会话超过 24 小时未活动, THEN THE 对话管理器 SHALL 自动归档该会话上下文并释放资源

### 需求 12：Prompt 模板管理

**用户故事：** 作为管理员，我希望能够配置和管理不同业务场景的 Prompt 模板，以便优化 LLM 在各场景下的回答质量和格式。

#### 验收标准

1. THE Prompt模板引擎 SHALL 支持管理员创建、编辑、删除和启用/禁用 Prompt 模板
2. THE Prompt模板引擎 SHALL 支持模板变量替换，包括用户问题、检索文档、对话历史和用户角色信息
3. WHEN 管理员创建新的 Prompt 模板, THE Prompt模板引擎 SHALL 提供模板预览功能，展示变量替换后的实际 Prompt 内容
4. THE Prompt模板引擎 SHALL 支持按业务场景（如技术文档问答、数据分析、流程指引）分类管理模板
5. WHEN 内部员工发起问答请求, THE Prompt模板引擎 SHALL 根据问题类型自动匹配最合适的 Prompt 模板
6. THE Prompt模板引擎 SHALL 为每个模板维护版本历史，支持管理员回退到之前的模板版本
7. IF 管理员未配置任何自定义模板, THEN THE Prompt模板引擎 SHALL 使用系统内置的默认 Prompt 模板

### 需求 13：LLM 调用安全约束

**用户故事：** 作为管理员，我希望系统对 LLM 调用实施严格的安全约束，防止 Prompt 注入攻击和敏感企业信息泄露到外部 LLM 服务。

#### 验收标准

1. WHEN 用户提交问题, THE LLM网关 SHALL 对输入内容进行 Prompt 注入检测，识别并拦截试图操纵 LLM 行为的恶意输入
2. WHILE 使用云端LLM 服务, THE 数据安全层 SHALL 对发送至外部 API 的内容进行敏感信息脱敏处理，移除人名、手机号、身份证号等个人隐私数据
3. THE LLM网关 SHALL 对每次 LLM 调用的输入和输出内容进行安全审计日志记录
4. WHEN LLM服务 返回的回答包含可能的敏感信息标记, THE 数据安全层 SHALL 在展示前进行二次过滤
5. THE LLM网关 SHALL 对单个用户每小时的 LLM 调用次数实施频率限制，默认上限为 100 次
6. IF Prompt 注入检测识别到高风险输入, THEN THE LLM网关 SHALL 拒绝该请求并记录安全事件日志通知管理员
7. WHILE 使用云端LLM 服务, THE 数据安全层 SHALL 确保传输的文档内容不包含标记为"机密"或"绝密"级别的信息

### 需求 14：内网部署离线 LLM 方案

**用户故事：** 作为管理员，我希望在纯内网部署场景下系统能够使用本地部署的 LLM 模型完成所有智能问答功能，无需依赖外部网络。

#### 验收标准

1. WHERE 选择纯内网部署方案, THE LLM网关 SHALL 通过本地部署的 Ollama 或 vLLM 实例提供 LLM 推理服务
2. WHERE 选择纯内网部署方案, THE 分析平台 SHALL 提供本地模型文件的离线导入功能，支持从物理介质加载模型权重
3. WHERE 选择纯内网部署方案, THE LLM网关 SHALL 支持本地模型的版本管理，包括模型更新和回退操作
4. WHERE 选择纯内网部署方案, THE 分析平台 SHALL 提供本地模型的 GPU/CPU 资源监控和性能调优配置界面
5. WHERE 选择纯内网部署方案, THE LLM网关 SHALL 支持同时加载多个本地模型并根据任务类型自动选择合适的模型
6. IF 本地模型推理服务不可用, THEN THE 分析平台 SHALL 降级为仅展示 RAG引擎 检索结果模式并通知管理员

### 需求 15：云部署 LLM API 调用安全

**用户故事：** 作为管理员，我希望在云部署场景下系统对外部 LLM API 的调用具备完善的安全保障机制，确保 API Key 安全存储和请求传输加密。

#### 验收标准

1. WHERE 选择云服务器加安全加固方案, THE 数据安全层 SHALL 使用密钥管理服务（KMS）加密存储所有 LLM API Key，禁止明文存储
2. WHERE 选择云服务器加安全加固方案, THE LLM网关 SHALL 对所有发往外部 LLM API 的请求使用 TLS 1.2 及以上版本加密传输
3. WHERE 选择云服务器加安全加固方案, THE 数据安全层 SHALL 支持 API Key 定期轮换机制，轮换周期可由管理员配置
4. WHERE 选择云服务器加安全加固方案, THE LLM网关 SHALL 仅允许从指定的内部服务网段发起外部 LLM API 调用
5. WHERE 选择云服务器加安全加固方案, THE 数据安全层 SHALL 记录每次外部 LLM API 调用的请求时间、目标服务、Token 用量和响应状态
6. IF API Key 泄露或异常使用被检测到, THEN THE 数据安全层 SHALL 立即禁用该 Key 并触发安全告警通知管理员

### 需求 16：Token 用量监控与成本控制

**用户故事：** 作为管理员，我希望系统能够监控 LLM 调用的 Token 用量并提供成本控制手段，以便合理规划预算和防止资源滥用。

#### 验收标准

1. THE Token监控服务 SHALL 记录每次 LLM 调用的输入 Token 数、输出 Token 数和对应的费用估算
2. THE Token监控服务 SHALL 提供按用户、部门、模型和时间维度的 Token 用量统计报表
3. WHEN 管理员设置部门或用户级别的 Token 用量配额, THE Token监控服务 SHALL 在用量达到配额 80% 时发送预警通知
4. IF 用户或部门的 Token 用量达到配额上限, THEN THE Token监控服务 SHALL 阻止该用户或部门继续发起 LLM 调用并提示配额已用尽
5. THE Token监控服务 SHALL 提供实时仪表盘，展示当前月度 Token 用量、费用累计和各模型调用次数
6. WHEN 管理员配置成本预算上限, THE Token监控服务 SHALL 在总费用达到预算上限时自动暂停非关键场景的 LLM 调用
7. THE Token监控服务 SHALL 保留至少 12 个月的历史用量数据供管理员进行趋势分析和容量规划
